## P2：应优先修复（Should Fix）

### R-01：服务模式切断演示编辑器的自定义图片链路

位置：[AssetsView.vue:56](D:/work/26.10.9/all/apps/admin/src/views/AssetsView.vue:56)、[AssetPicker.vue:27](D:/work/26.10.9/all/apps/admin/src/components/AssetPicker.vue:27)。

触发：在服务模式（Service Mode）上传新图片，再编辑图片题、课程封面或选手照片。上传仅写服务端，页面读取 `remoteAssets`；三个编辑器共用的选择器却始终读取 `demo.assets` 和内置示例。服务模式没有另一个本地上传入口，选择器仍提示“先在图片资源中上传”。

影响：既有演示编辑器无法继续添加自定义图片，只能使用旧缓存或内置示例。这是操作链路回归，不是要求三个模块提前接入真实后端。

证据：独立审查员追踪了上传、选择器和各编辑器的数据来源，协调者再次核对源码。

建议：保留明确标注的本地演示图片库／上传入口，服务首页继续使用服务图片库。不要直接把需要会话的私有预览地址保存为本地模块的长期媒体地址。回归测试（Regression Test）覆盖服务模式下演示编辑器新增自定义图片，同时确认首页不会错误引用本地图片 ID。

### R-02：图片列表旧请求覆盖新操作结果

位置：[AssetsView.vue:18](D:/work/26.10.9/all/apps/admin/src/views/AssetsView.vue:18)、[AssetsView.vue:58](D:/work/26.10.9/all/apps/admin/src/views/AssetsView.vue:58)。

触发：初次读取图片较慢时上传，上传后的第二次读取先返回，初次旧读取随后返回。上传按钮在初次加载期间仍可操作。

证据：从源码抽取 `load()`，在独立虚拟机（VM）控制两个 Promise，列表实际从 `[{id:"uploaded"}]` 变回 `[]`。加载、错误状态也没有请求代次保护。

影响：上传成功后图片看似消失；删除后也可能恢复显示旧列表。数据库没有丢失数据，页面却与操作结果相反。

建议：加入请求代次（Generation）检查，只允许最新请求更新列表、错误和加载状态；覆盖上传、删除、重试及旧失败响应迟到。小程序已有资源加载器可作为行为参考。

### R-03：认证查询故障被当成登录失效

位置：[router/index.ts:77](D:/work/26.10.9/all/apps/admin/src/router/index.ts:77)。

触发：用户已有有效会话，但导航时 `/api/admin/auth/me` 返回 503、超时或网络错误。守卫对所有异常都返回 `/login`。

证据：独立 VM 调用源码守卫，注入 `status:503`，结果确实跳转登录。

影响：临时服务故障把管理员送回登录页，没有明确原因；本地演示模块也无法导航进入，未保存表单可能因页面离开丢失。

建议：确认 401 才转登录；其他故障保持当前页面或展示可重试故障状态，同时继续阻止未经确认的受保护导航。测试区分 401、503、超时及恢复成功，不能简单放行所有异常。

### R-04：一条失败删除任务阻塞其他对象清理

位置：[platform.ts:259](D:/work/26.10.9/all/apps/server/src/platform.ts:259)。

触发：`ObjectDeletion` 批次中一个对象持续删除失败，循环直接抛错，中止后续项；下次继续遇到相同失败项。

证据：在操作系统临时目录启动独立 PostgreSQL 和 S3rver，实际写两个对象与两条清理记录，仅对第一对象注入故障。连续两次清理以及重建服务实例后，两条记录都仍存在，第二个健康对象仍可读取。没有使用用户数据库。

影响：已经逻辑删除的图片长期残留存储，任务积压、费用增加。数据库权限仍阻止通过图片 API 公开读取，未证明公开泄露。

建议：逐对象隔离失败，保留失败记录并继续；使用可推进的分页或重试时间，避免前 100 条失败项饿死后续任务。测试单项失败、其他成功、重启重试及超过单批容量的情况。

### R-05：过大 JSON 请求错误归类为 500

位置：[app.ts:35](D:/work/26.10.9/all/apps/server/src/app.ts:35)、[app.ts:97](D:/work/26.10.9/all/apps/server/src/app.ts:97)。

触发：合法 Origin 下向首页写接口发送约 70 KB 的 JSON，超过 64 KB 解析限制。

证据：独立 HTTP 探针保留真实 Nest／Express 解析与错误过滤器，只替换业务服务。实际响应为 `500 / HTTP_500`，提示服务不可用。请求解析器的过大输入异常（PayloadTooLargeError）不属于 `HttpException`，被统一归类为内部错误。

影响：违反 C-04 的 HTTP 状态约定；客户端无法区分输入过大与服务故障，重试也不能解决。

建议：显式识别已知请求解析异常，返回 413 等正确状态，同时保留错误包装与请求编号（Request ID）。已有过大 multipart 测试不能替代大 JSON 测试。

### R-06：可配置服务端口与固定网页代理不一致

位置：[vite.config.ts:9](D:/work/26.10.9/all/apps/admin/vite.config.ts:9)、[config.ts:44](D:/work/26.10.9/all/apps/server/src/config.ts:44)。

触发：为避开端口占用，把开发环境的 `PORT` 和 `PUBLIC_BASE_URL` 改为 3001，重启网页与服务。服务器读取 3001，Vite 的全部 API 和私有图片代理仍固定访问 3000。

证据：用合成环境调用 `readConfig` 返回 `port:3001`，对照固定代理目标确认冲突；没有修改用户配置或启动／停止其服务。

影响：非默认端口下，后台登录、配置、上传和预览无法连接正确服务。默认 3000 路径不受此问题影响。

建议：代理目标读取明确的开发配置，联动监听端口与公开地址；补充非默认端口验证。至少说明需要同步更改的配置位置。
